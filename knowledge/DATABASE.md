# Database

MySQL (dikunci standar Go skill, bukan pilihan bebas - lihat
`.claude/rules/database.md`). Migrasi di `apps/api/migrations/`,
dijalankan lewat `npm run migrate:up` (wrapper `scripts/migrate.mjs` di
atas `golang-migrate`).

| `guests` | guest | `token` UNIQUE + index (link personal tamu, wajib cepat di-lookup). `rsvp_status` ENUM cocok dengan `RsvpChoice` di `RsvpConfirmation.tsx`. Sejak migration `000006`: `gender` ENUM `male`/`female` **NULLABLE** (baris lama sebelum migration ini tetap NULL sampai disunting - tidak ada default yang akurat untuk gender), `invitation_type` ENUM `online`/`physical` NOT NULL DEFAULT `online`, `souvenir_type` ENUM `regular`/`vip` NOT NULL DEFAULT `regular`, `email` VARCHAR NOT NULL DEFAULT `''`, `address`/`notes` TEXT NULLABLE. Sejak migration `000007`: `attending_count` TINYINT UNSIGNED NOT NULL DEFAULT `1` (diisi TAMU saat RSVP `attending`, 1 atau 2 orang, untuk pax makanan - BUKAN diisi admin), `is_expected_attending` BOOLEAN NOT NULL DEFAULT `TRUE` (dugaan ADMIN, kolom terpisah dari `rsvp_status` milik tamu). Sejak migration `000014`: `checked_in_at` DATETIME **NULLABLE** - kehadiran NYATA di gate, dicatat menu Scan. NULL disengaja dan bermakna "belum datang"; jangan diubah jadi `NOT NULL DEFAULT`, karena justru NULL itulah syarat UPDATE bersyarat yang mencegah dua petugas saling menimpa jam kedatangan (lihat `BACKEND.md`). **Jangan tertukar** dengan `attending_count` (janji tamu saat RSVP), `is_expected_attending` (dugaan admin), atau `rsvp_status` (niat) - tidak satu pun dari ketiganya adalah bukti tamu benar-benar tiba. Sengaja TANPA index: satu-satunya jalur baca adalah lookup per tamu lewat `token`/`id` yang sudah ber-index. Sejak migration `000018`: `contacted_at` DATETIME **NULLABLE** - kapan admin membuka WhatsApp lewat tombol "Kirim Undangan" (`docs/plan/reservation-reset-contacted-flag/PLAN.md`). **Membalik K6 `og-share-image-dinamis`** ("pelacakan pengiriman: tidak dilacak... nol kolom baru di tabel `guests`"), yang bahkan menyebut persis "tidak ada kolom `invitation_sent_at`" - pembalikan dicatat, preseden yang sama dengan `000015`. Namanya `contacted_at` dan **bukan** `invitation_sent_at` dengan sengaja: `wa.me` tidak bisa melaporkan balik apakah pesan benar-benar terkirim (keterbatasan yang mendasari K6 itu TIDAK berubah), jadi yang tercatat hanyalah "admin membuka WhatsApp untuk tamu ini". Jangan pernah menyajikannya sebagai bukti terkirim. Sengaja TANPA index, alasan sama dengan `checked_in_at`. Sejak migration `000017`: `pax_quota` TINYINT UNSIGNED NOT NULL DEFAULT `2` - JATAH kursi undangan, diisi **ADMIN** (`docs/plan/guest-pax-quota/PLAN.md`). **Jangan tertukar** dengan `attending_count` (JANJI tamu, diisi TAMU): dua kolom, dua pemilik, dan `attending_count` tidak pernah boleh melebihi `pax_quota` - itulah yang ditegakkan `resolveAttendingCount`, yang sejak migration ini **tidak lagi** membatasi 1-2 melainkan 1..`pax_quota`. DEFAULT `2` menjaga perilaku lama persis tanpa backfill (pola `attending_count DEFAULT 1`). Rentang sah 1..20 ditegakkan `validatePaxQuota` di service, **bukan** skema. Sengaja TANPA index: satu-satunya jalur baca adalah agregasi full-scan `CountGuestsGroupedBySide` dan lookup per baris lewat `id`/`token` yang sudah ber-index. Sejak migration `000016`: `group_id` BIGINT UNSIGNED **NULLABLE** + index `idx_guests_group_id` + FK `fk_guests_group_id` -> `guest_groups(id)` **ON DELETE RESTRICT**. FK ini SAH karena `guest_groups` dimiliki modul `guest` yang sama (relasi INTRA-modul, bukan lintas modul). NULL disengaja: baris tamu yang sudah ada tidak diubah - mereka bergroup kosong sampai disunting, pola yang sama persis dengan `gender`. Yang MEWAJIBKAN group adalah `Service.Create`/`Update` (`validateGroupID`), **bukan skema** - jangan menjadikannya NOT NULL. `side`/`invitation_type`/`souvenir_type` BUKAN group: ketiganya ENUM bernilai tetap yang hanya bisa berubah lewat migration. Lihat `docs/plan/guest-fields-admin-layout/PLAN.md`, `docs/plan/dashboard-wa-rsvp/PLAN.md`, `docs/plan/scan-checkin-gate/PLAN.md`, dan `docs/plan/guest-groups/PLAN.md`. |
| `guest_groups` | guest | **Tabel kedua milik modul `guest`** (migration `000016`, `docs/plan/guest-groups/PLAN.md`) - satu modul boleh punya banyak tabel; yang dilarang aturan modular monolith adalah join/FK LINTAS modul. Sejak migration `000017`: `default_pax` TINYINT UNSIGNED NOT NULL DEFAULT `2` - angka AWAL jatah kursi untuk tamu baru di group ini, **bukan** batas yang mengikat anggotanya. Ini **membalik K3 guest-groups** ("tanpa warna, nomor meja, maupun kuota"); pembalikannya dicatat di `docs/plan/guest-groups/PLAN.md` K3 dan `docs/plan/guest-pax-quota/PLAN.md` §2 - preseden yang sama dengan migration `000015`. Group "Keluarga" ber-`default_pax` 4 tetap bisa berisi tamu ber-`pax_quota` 6 dan 1, dan itu justru alasan jatah tidak boleh hidup di group saja. `name` VARCHAR(100) NOT NULL **UNIQUE** (`uq_guest_groups_name`): dua group bernama sama membuat dropdown & layar scan ambigu; keunikan dicek lewat `GetGuestGroupByName` SEBELUM tulis, bukan menangkap error MySQL 1062 - pola yang sama dengan `admin_users.username`. `description` VARCHAR(255) NOT NULL DEFAULT `''` dan **bukan TEXT** - MySQL melarang DEFAULT pada kolom TEXT (itulah sebabnya `guests.address`/`notes` terpaksa `TEXT NULL` + helper `nullableText`). Dirujuk `guests.group_id` dengan FK **RESTRICT**; penolakan hapus yang enak dibaca ("masih dipakai N tamu") ditegakkan lebih dulu di service (`canDeleteGroup`), FK-nya lapis kedua untuk jalur non-aplikasi. |
| `admin_users` | auth | Dikelola CRUD lewat menu Pengguna (`docs/plan/admin-users/PLAN.md`) - TIDAK lagi asumsi "selalu 1 baris". Baris seed awal (`admin` / `ubah-password-ini` - **wajib diganti setelah deploy pertama**, lihat `migrations/000005_seed_admin.up.sql`) tetap ada sebagai akun pertama. `username` UNIQUE. Sejak migration `000015`: `role` ENUM `admin`/`scanner` NOT NULL DEFAULT `'admin'` - **membalik keputusan lama "semua admin setara/tanpa role"** (docs/plan/scan-checkin-gate/PLAN.md K2). `admin` = akses penuh; `scanner` = petugas gate yang HANYA boleh membuka menu Scan. DEFAULT `'admin'` membuat seluruh akun lama tetap admin penuh tanpa backfill. Tabel ini sengaja **tidak** punya relasi ke `guests`: check-in tidak mencatat siapa petugas yang memindai. |
| `whatsapp_config` | whatsapp | Singleton (1 baris, `id=1`, migration `000008`). `message_template` TEXT dengan placeholder `{nama}`/`{jumlah}`/`{mempelai}`/`{tanggal}`. `is_enabled` menghentikan pengiriman otomatis tanpa memutus tautan akun. |
| `whatsapp_send_logs` | whatsapp | `qr_payload` kini menyimpan `ELW1:<token>`, bukan lagi teks undangan (lihat `BACKEND.md`) - modul `whatsapp` memperlakukannya sebagai string buram dan **tidak berubah** karenanya. `guest_id` **primitif TANPA FK** ke `guests` (aturan modular monolith). Kolom snapshot (`guest_name`, `phone`, `qr_payload`, `couple_name`, `event_date_label`, `attending_count` - migration `000009`) WAJIB diisi supaya kirim ulang (`Resend`) tidak perlu membaca tabel `guests`/`invitation_content` milik modul lain. `status` ENUM `pending`/`sent`/`failed`, index di `status` & `created_at`. |

Tidak ada FK lintas tabel/modul (aturan modular monolith).

**Sesi WhatsApp (device & kunci enkripsi) TIDAK disimpan di MySQL** - library
`go.mau.fi/whatsmeow` hanya mendukung SQLite/Postgres secara penuh
(diverifikasi dari source `store/sqlstore/container.go`). Disimpan sebagai
file SQLite terpisah di `WA_STORE_DIR` (default `./wa-store/wa.db`),
di-migrate otomatis oleh whatsmeow sendiri (BUKAN golang-migrate). File ini
**wajib** ikut volume persisten di deployment - kalau hilang, akun WhatsApp
harus di-pairing ulang lewat scan QR. Lihat `docs/plan/dashboard-wa-rsvp/PLAN.md`.
